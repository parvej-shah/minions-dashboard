# Task 55: A picked layout shows at once; shorter real edit

## Why (measured, 2026-11-12)
- One tile = one satori render of the 1080x1350 cover, ~350 ms CPU locally. Drawing it smaller
  does not help (blank result with a scaled wrapper; rasterising is only ~25% of the time).
- Picking a layout runs the whole cover edit (reads, brand-image fetches, 1080x1350 render, R2 upload,
  DB write, R2 delete) and then a second GET of the asset: the picture changed only after all of it.

## Decision (user, 2026-11-12)
Preview tiles are NEVER stored in R2 (storage cost). An earlier version of this task stored them and
pre-warmed them; it was removed before commit. Tiles stay render-on-request, browser-cached.

## Changes
1. **Instant pick**: the tile already on screen is shown in the cover preview the moment a layout is
   clicked ("Sharpening" badge); the real cover replaces it. Only if the tile's words are current.
2. **Client**: the new cover shows as soon as the POST returns; the asset refresh no longer gates it.
3. **Server**: brand images (headshot, cut-out) are reused for 60 s per instance; the replaced
   cover is deleted in the background (`src/lib/background.ts`, Next `after`).
